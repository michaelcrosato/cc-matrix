# Shared garden authority

The unmodified AI Hub Session Protocol v1 client is `vendor/hub/session.js`, client 1.4.0, repository commit `35a1047f2067b2af3de3943f0fe452f39105d869`. The companion harness, bridge and round coordinator are vendored together. They use same-origin HTTP; the playable artifact itself also runs from `file://`.

`NightNet.connectHub(callbacks)` connects using `mode: shared-world` and seats `[1,2]`. `onConnect(info, session)` constructs the world before the SDK's single automatic `ready()`. Start remains gated by `AIHub.time() >= 0`. A server has `session.server === true`, `localIndex === -1`, and no local commands. Names supplied by Hub must be drawn as text, never inserted as HTML. While active, network access uses only AIHub; direct peer setup explicitly rejects it.

The authority steps `NightSim` at 120 Hz. Call `session.tick(dt, localAction, world)` each native update, then step the host world with `session.inputs` only when `session.canStep()` is true. Guests submit intentions at 15 Hz. The authority snapshots at 12 Hz. A sequence number rejects old/replayed commands; the cumulative ray counter is repeated so packet loss cannot permanently swallow a press or duplicate a ray. Axes must be finite and bounded, are normalized diagonally, and are tied to their sender's stable seat. Inactive remote movement and Focus release after 450 ms. A departed seat is neutral immediately. A guest cannot send position, health, damage, charge or score.

Presentation snapshots use compact column arrays and round world coordinates to hundredths. They carry all entities, fixed geometry, campaign phase, score, seed/tick, bee counts, formation, charge and recent one-shot events. Each is independently complete. Snapshots under 1,200 UTF-8 bytes use unreliable delivery; larger ones deliberately use ordered reliable delivery, below the SDK's 16,384-byte limit. A rolling sender guard permits at most 19 gameplay packets/second, preserving lifecycle headroom. Diagnostics report maximum packet size, rate, rejected packets and stale neutralizations. `session.view()` smooths guest positions and provides a small local movement prediction; damage and contact remain host decisions.

On clear/failure/time-up the host calls `session.finish(world, won)` exactly once. A reliable final world reaches remaining guests before they acknowledge it; the host then reports the result. A 450 ms fallback reports exactly once even if an acknowledgement cannot arrive. Late snapshots cannot overwrite the final phase. Hub results give every remaining player the same score and tied standing. `end` removes handlers and stops traffic. Shared-world menus may show settings but must not freeze the authority. Hub's Create+Options chord must be reserved by input integration.

## Direct peer setup

`new NightNet.DirectPeer(callbacks)` is available only outside Hub. Host calls `createOffer()`, guest calls `acceptOffer(offerCode)` and returns the resulting answer, then host calls `applyAnswer(answerCode)`. The `KBN1.` codes contain bounded, validated SDP only. No broker, room service, STUN service, TURN server or credentials are used. This supports local/browser-to-browser links where ICE host candidates can reach one another. Arbitrary internet/NAT connectivity is not guaranteed.

The single ordered `killer-bee-night` data channel carries the same action/snapshot contract. On connection, `peer.session` is a two-player Session with host seat 0 and guest seat 1. A final world/result is sent reliably, acknowledged by the guest, then both close; a two-second fallback bounds teardown if the acknowledgement cannot arrive. Cancellation closes data channel and peer connection and invalidates asynchronous setup operations. Malformed/wrong-step codes throw a short recoverable message. Setup UI should retain a selectable code field so manual copy/paste works when clipboard permission fails.

## Test entry points

`tests/network-unit.mjs` verifies validation, command ownership/sequences, stale releases, Hub start/end/finish gates, compact snapshots and signaling codes without a browser. `tests/network.py` uses the pristine real harness and real loopback WebRTC browser contexts. The project test command wraps these quietly and saves detailed evidence. Browser emulation cannot prove real-device controller support, subjective audio, or arbitrary internet reachability.
