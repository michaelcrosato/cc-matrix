# Matrix Dashboard

Run every combination of model × effort × prompt variant headless through Claude Code, Codex, Grok, Antigravity (`agy`) and Muse Code, then play, score and compare the results. No dependencies beyond Node 18+.

## Start
Put all files in one folder, then:

- **Ubuntu / macOS:** `./start-dashboard.sh`  (or `node dashboard.mjs --open`)
- **Windows PowerShell:** `.\start-dashboard.ps1`  (or `node dashboard.mjs --open`)

It opens http://localhost:4173. Options: `--port 5000`, `--config other.json`, `--out other-runs`, `--allow-host name` (see Notes).
`claude`, `codex`, `grok`, `agy` and/or `muse` must be installed and logged in on the same machine.

The page updates by itself: runs finishing (also ones started with `node run-matrix.mjs` in a terminal), scores saved in another tab and hand edits to the config or prompt show up within a couple of seconds, without losing what you're typing. It works on phones, tablets and wide screens.

## Tabs
Think of each run as a terminal session you'd otherwise start by hand: `cd` into a fresh folder, start a CLI with a model and effort, give it the prompt. The dashboard only queues those sessions (Run → Preview shows them as the commands they stand for). A multistage run is several in a row, each picking up a copy of the folder the one before left.

- **CLIs** — what this machine can run. The **CLIs** card shows which CLIs are installed (version, with an **update** button for Claude Code, Codex, Grok and agy that runs the CLI's own `update`; it's off while a batch or test runs, and Muse is updated by hand), the models each offers (click one to add it) and the global instruction files each loads. **This computer** shows what the agents are told about this computer where the prompt says `{{machine}}` (its file in `environments/`, below), as they get it, with when it was checked; **Check again** runs `node check-environment.mjs`. With no file for this computer, or one checked more than 14 days ago, it says so, and so do the Run tab and Start when the prompt uses `{{machine}}`. **Models**: one dropdown per row picks the model (Claude 5.5 family, GPT-6+ on Codex, Grok 4.7, Gemini 3.8 Flash and Gemini 4 Argon on agy, Muse Spark 1.3 and Muse Wonder 1.0; the list is `CATALOG` in `dashboard.html`, and Codex adds any newer GPT-6+ model it lists; only the newest of each GPT line is offered, e.g. gpt-6.1-sol and not gpt-6-sol), which sets the CLI, model ID and run name. **Custom** (bottom of that list, one per CLI) gives a box to type any model ID. Each effort level is its own dropdown holding only the levels that model takes ("+ effort" adds another to sweep; Claude Code also offers each level with Ultracode). Then an optional time limit, and **Test**: one tiny task through the real command line and parser, about a minute, to check install, login, model ID, flags and that results are read. Tick "Test with /goal" to test the goal loop too. 1-shot runs sweep these models at the efforts set here; the stages in Setup · Advanced pick from them at any effort they take. **CLI commands and flags** holds each CLI's executable, the extra flags added to every run of it and its **Max per model**: at most that many runs of one of its models at once, whatever their effort, for a plan whose limits are per model (Codex's start failing at 4 runs of one model, so 3 there: 3 of GPT-6.1 Terra, 3 of Sol and 3 of Astra can still run beside each other). It's `perModel` in the config (`{ "codex": 3 }`), applies to batches started in a terminal too, and to batches already running from the next run that starts.
- **Setup · Basic** — the 1-shot prompt: dimensions and their variants (**Bulk add…** takes a pasted list, one per line, e.g. 100 games for `{{source}}`: each line's text becomes a variant with a short name made from it, or write `short | text`; numbering, bullets and lines already there are skipped, and a text that ran before gets its short name back; **+ Add…** offers your **pinned** variants for the field, then the variants finished runs used that the dimension doesn't have now, labelled as in Results' filters; picking one adds it with its name and text, and a text that ran keeps that name, so its runs count for it. Each variant multiplies the runs, so they're offered, not added. Pin the ones you use often with **pin** on a variant's row, or any of the field's in **+ Add… → Pin or unpin…**; pins are saved in the config as `pinned` (`{ "genre": [{ "id", "text" }] }`), and a config without them starts from `DEFAULT_PINS` in `dashboard.html`: "use the source", "your choice" and, for perspective, art and animation, "use the engine", plus off switches like no goal), the prompt and the file it's saved to. **Prompt history** lists the prompt's versions (v1, v2 …): when each was last edited and first ran, what changed from the one before (fields added or removed, lines), how many runs used it, and buttons to view it or see the changes. A version gets its number when a batch first runs it, so all the edits between two batches make one version; until then it shows on top as the next run's version, saved edits or not. Ctrl+S saves. Errors (like a `{{placeholder}}` with no dimension) block saving; warnings flag efforts or models a CLI won't take and CLIs that aren't installed.
- **Setup · Advanced** — multistage runs: the stages (plan, build, content…) that hand the work from one model or lab to the next, which models and efforts run each, what each is told and when it's done. **Who runs each stage** spells it out: each stage's models, how many sessions it makes per brief and every path a brief takes. See Runs in stages.
- **Run** — two views, switched at the top, where **⏸ Pause**, **■ Stop** and **⟳ Restart dashboard** also are: **Monitor**, the batch going (or the last one; it shows by itself while one runs), and **Set up**, what the next batch runs (it shows otherwise; Start and + Queue go to Monitor). In Set up: **Basic · 1-shot** or **Advanced · multistage** (when there are stages). In Basic, tick the model+effort pairs and variants you want; in Advanced, pick models per stage (see Runs in stages). **Preview** shows the sample prompt and the batch as terminal sessions: each run's folder (for a later stage, a copy of the one it continues from) and the exact CLI command with what it's sent. The count updates live and skips runs already finished (and says how many of those were made with an older prompt or a variant's old text). Each model shows whether it works (passed a test or has finished runs). Runs take turns across CLIs, so parallel slots go to different services, and start at least 3 seconds apart (see Run folder names); **Max per CLI** caps one CLI to stay inside its plan's rate limits, and a CLI's **Max per model** (CLIs → CLI commands and flags) one model of it. **Priority** (folded away until you open it) sets which runs start first and can hold some back (see Priority). Preview shows the exact prompt. Start / Stop, with a live log. While a batch runs, **+ Queue** adds another beside it (see Queued batches). **Once a run starts, its model, effort, prompt and time limit are fixed and it runs to the end; nothing running is ended unless you confirm it.** **While a batch runs, Options act on the runs not started yet** (Repeat is fixed once it starts), and every change asks first: **Parallel runs** and **Max per CLI** go up or down, and lowering one below what's running asks whether to let the extra runs finish (no new one starts until there's room) or to end the newest and start them over later; a new **time limit** asks whether it's for runs that start from now or the running ones too (counted from when each started; one already past it ends as timed out); a new **budget** shows what's been spent and what the change does first, and raising a spent one lets runs start again (spend is counted as each run finishes, when the CLI reports it, so the budget never stops a run that's going and one can take it past the budget; a run ended early isn't counted, though it spent); **Retry failed** turned on queues the failed runs skipped earlier, and so does **Resume failed** for the ones it can resume (see Resuming failed runs). **Pause** holds the queue: the running ones finish, or end them to start over when you resume. Each running run has ↻ (end it now, start it over later in this batch) and ✕ (end it now, leave it for the next batch), and each CLI's tally has **skip rest** to leave its queued runs out of this batch. A running agent can't be frozen and picked up where it left off (its time, tokens and cost would then describe two sessions), so a run ended here always starts over (a resumed one is resumed again instead); every choice that ends one says so, in red. **Stop** offers Pause first. Quitting or restarting the dashboard is different: the batch is kept to pick up, and a Claude Code session it cuts off carries on where it was (see Restarting the dashboard); Ctrl-C in the dashboard's terminal asks to be pressed again while agents are running. **Monitor** shows the batch in cards: **This batch** (every run it has as one bar, done OK or failed, going, queued and on hold, its spend, reported and at list price, how long it has run and roughly how long is left, why runs aren't starting when they aren't, and warnings: a CLI whose last 3+ runs failed or that fails most of its runs, with the likely cause, a run going 2× longer than usual for its setup, finished runs that look off, and the batches queued together); **By model**, each model and effort, by stage, with its runs done OK, failed, going, queued and on hold, the median time and list price of the ones done, how many met their /goal, games that threw when loaded, the latest failure's cause, and **Results →** to see them there; **Running now**, longest first, each run's brief (the variants that differ between them), when it started and how long it has run against its setup's usual time, **out** (what its CLI has printed so far), ↻ and ✕; **Failures**, by model and cause, most first, each with its latest error; **By CLI**, each CLI's tally with **skip rest**, its plan's limits as its latest run saw them (5-hour and weekly use, and when each resets), Codex's credit balance from its session logs (past its plan's limit Codex spends credits, which no run's cost counts) and how much this batch has used, and a line when its last runs failed on a limit; the batch's **Options**; and the **Log**. On a phone the tables are lists, two lines a run. The header pill and the browser tab's title carry the progress and ⚠ too. A CLI that isn't installed has its runs skipped (not failed).
- **Results** — filter by anything (including CLI and prompt version; on phones the filters fold behind a button, and each run is a card). **Compare** shows how B differs from A on any field: model + effort (opus · medium → sonnet · medium), effort (medium → high), a variant, CLI or prompt version, optionally **for each** value of another field. Effort medium → high for each model shows which model gains more from extra effort. **Only matching variants** pairs runs that differ only in what's compared; a change in bold goes the same way in at least 80% of 3+ pairs. **Averages by group** gives plain averages (time, cost, list price, output tokens, score, delivered %). Each run's **list $** is its tokens at the labs' public API prices (see What each CLI reports), so it compares across CLIs; its details add model requests, tool calls, compactions, subagents and the plan's usage. ⚑ marks a flagged run (see Insights), ⟳ a resumed one and "resumable" a failed one Resume failed can carry on with (filter or compare by **resumed**). ▶ plays the game, details shows everything about a run, reply shows the agent's Source Information and feedback, interview its exit interview (`exit-interview.json`, see The record in each game), failed runs show why, `out` shows the raw CLI output. Score out of 10 and add notes while you play. Variant columns that are the same for every run shown are named once above the table instead of on every row. **Columns** shows, hides and moves the table's columns (or drag a header onto another), freezes the first ones on the left so they stay while the table scrolls sideways (the first three, ▶, model and effort, by default; 📌 on a column freezes up to it), and offers more that start hidden: CLI, model ID, started, input tokens, requests, tool calls, compactions, context window, game errors, lines, CLI version and prompt version. They're kept per browser; **Reset all** goes back to the defaults. On a phone each run is a card, in its own order.
- **Insights** — what the runs say without playing them all. Filter by time (all, last 24 hours, last 7 days, last batch) and any field.
  - **Expectations** checks what should hold: more effort brings more output and time (same model, matching variants), finished runs leave a game file, a final reply and the exit interview their prompt asks for, no TODO/FIXME left, games load and run headless without errors (the game check, when it's on), repeats of a setup agree, one prompt version, and each CLI on one version.
  - **Needs a look** lists finished runs that look off, worst first: no game, no reply, no exit interview (or one that isn't valid JSON), no planner's review where its instructions ask for one, a /goal that was never met, a game that throws, logs an error or fails a request when the runner loads it (the game check), TODOs left, a time, cost or output at least 2× off what's usual for its setup, or a game under half the usual size. Big games aren't flagged, since bundling the libraries is allowed. A score, a note or "looked at" clears one, and the tab's badge counts the rest.
  - **Typical runs to score** picks, per model + effort, the run closest to usual: scoring it says the most about that setup.
  - **What the agents said** reads every answer to one question across the runs in view, by model + effort: each exit interview's lists (Testing, Engine and Prompt Feedback …, each answer paired with the question it was sent) and the planners' reviews of their prompt. **Search** finds a word in all of them, and the list of questions then says how many answers have it; **Copy** puts the answers shown on the clipboard as plain text, to paste somewhere else. The answers come from `/api/feedback`, read when the tab first shows them and again when runs change.
  - **What each choice changes** estimates each model, effort, Ultracode, variant and prompt version against a baseline, with everything else held equal.
  - **Spread** shows every run as a dot per group, for any measure.
  - **Over time** shows runs finished per hour or day, OK vs failed, per CLI.
  - **Failures** groups failed runs by cause: rate limit, login, model, time limit, network…

  "Usual for its setup" is learned from all finished runs with a robust model (median polish in log space) over model+effort, each variant and the prompt version, so it works even for a combination that ran once. It waits until each part has 3 finished runs.
- **Audit** — findings from the latest audit of this repo or its runs (`audit.json`): what was found, what was done, what's left for you to decide and how it was checked. Tick each one as read. The tab only shows when `audit.json` exists. Its text takes a little Markdown: `code`, **bold**, lists (one level of sub-items) and simple tables.

## The CLIs
| CLI | Command per run | Prompt goes in | Cost | Efforts |
|---|---|---|---|---|
| Claude Code | `claude -p --output-format stream-json --verbose --model M --effort E` | stdin | reported | low, medium, high, xhigh, max (+ `-uc`) |
| Codex | `codex exec --json -m M -c model_reasoning_effort=E -` | stdin | — | per model (`codex debug models`), e.g. low … max, ultra |
| Grok | `grok --prompt-file prompt.md --output-format streaming-messages-json --model M --reasoning-effort E` | file | reported | low, medium, high, xhigh |
| Antigravity | `agy -p PROMPT --output-format stream-json --model M --effort E` | argument | — | per model (`agy models`), e.g. low, medium, high |
| Muse Code | `muse exec --json --model M --reasoning-effort E --prompt-file prompt.md` | file | — | minimal, low, medium, high, xhigh, max |

Plus each CLI's extra flags (CLIs → CLI commands and flags). The defaults turn permission prompts off, which a headless run can't answer: `--dangerously-skip-permissions` (Claude Code, agy), `--yolo` (Codex: no prompts, no sandbox, runs outside a git repo), `--always-approve` (Grok), `--yolo` (Muse). Runs being isolated (the default; see Notes) adds `--strict-mcp-config` (Claude Code) and `--no-foreign-personal-context` (Muse) and sets a few environment variables.
- **agy** model IDs are the base name, like `gemini-4-argon` or `claude-sonnet-5-5`, with the effort separate; `agy models` lists them with the effort appended (`gemini-4-argon-high`). It also serves Claude and GPT-OSS models; `{{lab}}` follows the model, not the CLI.
- **Muse** models: `muse-wonder-1.0` (default), `muse-spark-1.3`, `muse-spark-1.2`. It reports how much of the plan's allowance is used, not a cost.
- **Grok** models: `grok models`.

## What each CLI reports
Every run records tokens, time and outcome. This is what else each CLI gives, where it comes from and what it leaves out (checked 2026-10-29 with the versions in the table):

| CLI (version) | Cost it reports | Plan usage (`plan`) | Also recorded | Read from | Left out |
|---|---|---|---|---|---|
| Claude Code (2.1.312) | yes, at API list price, per model | 5-hour and weekly %, at the start and end | requests, tools, failed tools, compactions, first-token time, subagents | the stream (`stream-json`) | nothing found: its totals include subagents and helper models (the /goal checker, Haiku) |
| Codex (0.165.0) | no | weekly (and 5-hour) %, at the start and end; plan type | requests, tools, subagents, first-token time, context window | `exec --json` + its session logs (`~/.codex/sessions`) | its printed usage is the main thread only; subagents (it starts them at high efforts) are read from the logs and added. A run stopped mid-turn (by the time limit, say) prints none, so its main thread's usage comes from the log too |
| Grok (1.0.70) | yes, at its own rate: 34% of grok-4.7's list price (Oct 2026) | none found | requests, reasoning, tools, failed tools, compactions, /goal helpers | the stream + its session logs (`~/.grok/sessions`) | its stream is the main session only; /goal's planner, verifiers and summarizer run as sessions of their own, read from the logs and added (+43% cost on a long run) |
| Antigravity (1.4.10) | no | none | requests, tools, failed tools | the stream (`stream-json`) | nothing found (no subagents seen yet) |
| Muse Code (1.4.14) | no (allowance only) | 5-hour-style window and weekly %, tier | requests, tools, failed tools | `exec --json` | helper sessions on `muse-spark` aren't in its stream (2 in the run checked, ~2% of its tokens) |

- **`apiCostUsd`: the price on every run.** The run's tokens at each lab's public API list price (standard tier and context length; no batch, priority or long-context rates), so runs compare across CLIs whatever each one reports or bills. Claude Code's own cost is already at list price, so for its runs it's that cost. The prices are in `PRICES` in `run-matrix.mjs`, with the date checked; add or override models in `matrix.config.json` under `"prices"` (`{"model-id": {"input": 2, "cachedInput": 0.1, "output": 10}}`, USD per million tokens; a list of them with `from` dates for a price that changes, like Gemini 4 Argon's introductory price until 2026-11-30). A model without a price is listed in `unpricedModels`. On a subscription none of this is what you pay; it's what the same work would cost through the API.
- **Plan usage** is the account's, not the run's: how full each limit window was as the run ended (`usedPct`) and as it started (`startPct`, where the CLI says), and when it resets. With integer percents, a single run often moves it by 0 or 1.
- `helpers` has what was added from session logs (agents, tokens, requests, cost), so the CLI's own figure is the total minus that. `sessionLog` says whether the log was found; a run whose log is gone keeps the CLI's own figures.

## Ultracode and /goal
- **Ultracode (Claude Code only):** write an effort as `high-uc` (any level + `-uc`), or pick a "+ Ultracode" level in a model's effort dropdown in CLIs → Models. It's passed as `--settings {"ultracode":true}`; every other Claude run gets `{"ultracode":false}` so a global setting can't leak in. The `ultracode` column lets you compare on vs off. Other CLIs skip `-uc` efforts.
- **/goal:** the `goal` dimension. An empty variant means no goal. With text, the prompt is saved as `TASK.md` in the run's work folder and the agent is sent `/goal Read TASK.md … Done when: <your text>`. A command only works at the very start of the message and everything after it becomes the condition (max 4,000 characters), so it can't simply sit inside the main prompt. Add "or stop after N turns" to cap it.
- Claude Code, Grok, agy and Muse all run /goal headless, each with its own goal loop (Grok plans, builds and verifies with extra agents, so it takes longer and costs more). Codex has none, so its runs of a goal variant get the same prompt without /goal (marked * in the Run tab, `goalSkipped` in `result.json`).

## The prompt is its sections
Every section of the prompt is a dimension: the source, genre and perspective, game title, package, tech stack and so on, down to the three feedback lists. `prompt-template.md` holds only the headings and one `{{placeholder}}` per section, in order; each dimension's variants hold the section's text. So any section can be varied like any other: add a second variant to `scope`, say, and every combination runs with both.
- **Order:** the prompt is built in the dimensions' order. Drag a dimension by its ⠿ in Setup (or use ↑ ↓; touch screens have only the arrows) and its section moves in the prompt too: a section is its placeholder's line with the heading and blank lines above it. Setup warns when the prompt's sections are in another order (after a hand edit, say) or can't be moved (a placeholder on two lines, or two on one line). A new order is a new prompt version.
- **Placeholders inside a variant** are filled too: a section can say "a spiritual successor to {{source}}" or name the file `…-{{model}}-{{effort}}-{{stamp}}.html`. Setup flags any placeholder that isn't a dimension.
- **Run folder names** (Setup · Basic; `folderName` in the config): a run's folder is its model and effort, then the variant of each dimension ticked **in folder name** (`folderName.fields`; none by default), the date and time it started (`date`, the same `YYYYMMDD-HHMMSS` as `{{stamp}}` in the game's file name) and, once it has finished OK with its game, the game's title (`title`): the agent picks the title while it works, so the folder is renamed to add it, e.g. `claude-opus-5-5-xhigh__20261101-153012__MothOfTheWild` (with the source ticked, `claude-opus-5-5-xhigh__zelda-botw__20261101-153012__MothOfTheWild`). The runs of a batch start at least 3 seconds apart (`startGap` in the config, in seconds; `0` starts them together), so no two get the same time. Dimensions left out become a short code (`x` + 6 characters) when two runs could otherwise share a folder: when one of them has more than one variant, and for a stage after the first (it also records the steps before). Finished runs are recognised by the fields saved in their `result.json`, never by folder name, so changing this only names runs made from then on. Configs without `folderName` keep the older scheme: every dimension except those in `omitFromName`, no date or title, the code whenever something's left out. A folder that holds a different combination's run is never cleared to make room.
- **Older runs** count as each new section's only variant (`olderRuns`), so splitting the prompt into sections redid nothing.

## Runs in stages
A second way to run: one model plans, others build that plan, others again add content to each build, each step by the model best at it. For example, plan with Opus at max, build with Opus at xhigh, add content with GPT-6.1 Sol at max or Sonnet at medium.
- **Setup · Advanced** lists the steps in order, each with its **models** (any model in CLIs → Models, at any effort it takes), its **Instructions** (what its runs are asked to do: their message, or `STAGE.md` when the stage has a goal), an optional **Done when (/goal)** (the condition Claude Code checks each time the agent tries to stop, sent as `/goal`; Codex never gets it) and whether it makes a game (a plan doesn't). Every model of a stage runs it on every session of the stage before, and a stage with no models stops the chain there (leave content without models to stop after the build). **Add plan → build → content** starts from three ready-made stages to edit. A stage's text and goal can use the dimensions, the run's own placeholders and the step it continues from: `{{parentModel}}`, `{{parentEffort}}`, `{{parentStage}}`, `{{parentAgent}}` and `{{chain}}` (every step so far).
- **Run → Advanced · multistage** ticks which of each stage's models to queue, for every brief (the variants ticked below): with 1 plan model, 2 build models and 2 content models that's 1 plan × 2 builds × 2 content passes = 4 games. A stage with nothing ticked contributes the runs it already has, so you can plan today and build tomorrow, or add another content pass to builds you already like. The page counts what a batch would run before you start it.
- **What each run gets:** a stage after the first starts from a copy of the work folder of the run it continues from (without `node_modules`, `.git` and its `exit-interview.json`, and its games as their agent left them, without the record of the run before), so a build sees `PLAN.md` and a content pass sees the game. It finds `TASK.md`, the prompt filled for *this* run (so its file name and Source Information name this model), and is sent its stage's text. With a goal, on Claude Code, Grok, agy and Muse, the text is `STAGE.md` and the message is `/goal Read STAGE.md … Done when: <goal>`; Codex gets the text alone (`goalSkipped`).
- **Order:** a run starts once the run it continues from has finished OK, in this batch or an earlier one. If that one fails, the runs after it are left out of the batch (and run next time).
- **What's recorded:** `stage`, `chain` (each step's stage, model and effort), `parentId` (the folder it continued from) and `parentStartedAt` (details warn when that run has been redone since). A plan run has `expectsGame: false` and `planChars`; its missing game isn't flagged. A later stage's game is the one it made or changed (`entry`), not one it was given, and its record has every step's time, tokens and cost, the plan's included, and them added up (`stages`; see The record in each game). Results gets **stage** and **from** columns and filters for stage, what a run continues from and its whole path; details show the path with links up and down it. Model + effort groups and compares within a stage.
- **Folder names:** `<model>-<effort>.<stage>`, then as for any run (see Run folder names), with the code for a stage after the first, so the same builder on two plans gets two folders. Runs are known by their chain and brief, so the same picks find finished runs done. `--repeat` isn't used for stages.
- **A stage's name follows its text and goal**, as a variant's short name follows its text (see Notes): runs are known by their chain, which names each step's stage, so a name stands for one text. Editing a stage that has finished runs in Setup · Advanced gives it a new name as you type (`plan` → `plan-v2`, `-v3` …), so the new text runs on its own while those runs keep theirs; putting the old text back puts the old name back, and a name typed by hand stays. Names are letters, numbers, `-` and `_`. Each stage run records `stageHashes` (a hash of its stage's text and goal), so Results marks a run whose stage was edited since ("old text"), and Setup warns about a stage edited by hand in the config while it has runs.

## Queued batches
While a batch runs, **+ Queue** on the Run tab adds another beside it: tick what you want (1-shot or in stages), change Setup or the prompt first if you like, and queue it. Each batch is a runner of its own (`run-matrix.mjs --broker`) working from a copy of the config and prompt as they were when it was started or queued, so you can change them for the next batch straight away.
- **Slots:** the batches share Parallel runs, Max per CLI, Max per model, the budget, the time limit, the start gap, Pause and Priority (Options while they run), which the dashboard keeps for all of them. They get slots in the order they were queued, and a later batch only gets the ones the batches before it can't use: their running runs, and every run they still have to start, keep theirs (up to what each CLI may run at once). So a queued batch never holds up an earlier one: a build waiting two hours for its plan starts the moment the plan is done, while a batch with nothing to wait for ramps up at once in the slots that are left. Runs still start at least 3 seconds apart across all of them (`startGap`), the earlier batch's first.
- **No run twice:** a queued batch leaves out the runs an earlier one has queued or running, and a run of it that continues from one of those (a build on a plan being made there) waits for it there.
- **Monitor** lists the batches and how far each is (in This batch); **take out** leaves out the runs one hasn't started (its running ones finish; they run next time). **Stop** stops them all. The budget counts what all of them spend.
- Runs are matched by short name, so to run a variant's new text beside a queued batch that has its old text, give the variant a new short name.

## Priority
**Run → Options → Priority**, folded away until you open it (most batches don't need one), sets which runs start first. It's a list of rules, top first. Each names any of a CLI, a model, an effort and a stage (the rest left as "any"), and a run follows the first rule it matches. Runs start rule by rule, then every run no rule names; within each, they take turns across CLIs as they do without a priority. "plan-v2" first starts every plan before any build (without it, each CLI's runs go brief by brief, so the last briefs' plans wait behind every earlier build); "claude-opus-5-5 · xhigh" first gets that setup going early, to catch a problem before the rest have spent much.
- **It only orders.** Parallel runs, Max per CLI, Max per model, the budget, Pause and a build's plan still decide whether a run can start, and when the first in line can't, the next one that can takes the slot, so no slot sits idle waiting for it.
- **Hold** on a rule keeps its runs from starting until you untick it (the ones running finish): a CLI out of quota until its limit resets, say, without leaving its runs out of the batch the way **skip rest** does. Held runs don't keep slots from a queued batch. Live shows how many of each CLI's queued runs are on hold, and says so when every run left is.
- **When it applies:** set before Start, it goes with the batch. While batches run, Options shows theirs, and edits are a draft until **Apply**, which asks first; it applies to the runs not started yet and stays for the next batch. Each batch follows it, and batches still go in queue order. Preview lists the sessions in its order, the held ones marked.
- **In a terminal:** `--priority "stage=plan-v2; cli=codex hold"`: rules split by `;`, each its `key=value` pairs (`cli` or `provider`, `model` or `agent`, `effort`, `stage`, or any dimension, like `source=FarCry2`) and `hold`; or the JSON the dashboard sends (`[{ "match": { "stage": "plan-v2" } }, { "match": { "provider": "codex" }, "hold": true }]`). A batch from a terminal leaves held runs out, since nothing could lift the hold.

## Restarting the dashboard
**⟳ Restart dashboard** (Run, at the top) starts the dashboard again with its code as it is now (`dashboard.mjs`, `run-matrix.mjs` and the page, which reloads itself once it's back; with unsaved edits or a dialog open it asks first), so a change to them takes effect without losing the batch. `node dashboard.mjs` keeps the dashboard in a child process of its own for this and starts it again when it asks.
- **A batch going picks up where it left off by itself** once it's back, in a few seconds: the same batches with their settings (Pause too), log, spend and copies of Setup and the prompt. Its runners skip what's done, carry on what was cut off and start the rest.
- **Runs going are cut off.** A Claude Code session that has had its first answer carries on where it was (`claude -p --resume`, sent its `/goal` again or "continue where you left off"), work folder and all; only the request it was waiting on is asked again. A run of another CLI, or one that hadn't had an answer yet, starts over, and Restart says which before you confirm. With runs going it offers **Restart once they have finished** instead: no new runs start meanwhile, so nothing is cut off (**Restart now** or **Call it off** while it waits).
- **Quit (Ctrl-C) cuts them off the same way**, but the dashboard doesn't come back by itself. The next time it starts, the Run tab offers the batch under **Pick up where you left off** (what's finished, what's left, which cut-off runs carry on and which start over), with **Resume the batch** and **Forget it**. So it does after a crash or the computer going down: the session is saved as it changes (`runs/.session.json`), and an agent still going after its runner was killed outright (nobody can hear it any more) is ended before its session carries on (Linux).
- **A cut-off run whose agent finished on its own** (the terminal running the dashboard was closed, say, and the agent kept working until it was done) isn't sent anything again: whenever a batch has it, or with `node run-matrix.mjs --fold-ended`, its last session is read from its transcript (its cost from the totals Claude Code saved as it ended, its tool calls and final reply too) and added to its record like a resumed one's (`endedAlone` on that part). Finished on its own means its last answer called no tool, Claude Code saved its totals after it and, with a /goal, the goal was met, Claude Code ended the turn itself after 9 blocked stops, or an error ended it; a goal check that wasn't met means it was cut off before it could carry on.
- **A cut-off run carries on whenever a batch has it**, Resume failed or not; Forget it doesn't change that, and Start or Preview count it. Until then it isn't a result (Results, Insights and the report don't count it): its folder holds `unfinished.json`. A run still going in another runner is left out of a batch.
- **What's recorded:** a cut-off run that carries on is one run, like a resumed one: ⟳ in Results, its sessions in `parts` (the cut-off one has `cutOff`), its time, tokens and cost added up. A session cut off never printed its totals, so its tokens are its responses' in its transcript (`~/.claude/projects`) and its cost is those at list price, which is what Claude Code reports too (`costSource: estimated`); if Claude Code saved the session's totals as it stopped (a `cost-state`), those count instead. Ended mid-way (Stop, ↻, ✕) as it carries on, it stays cut off and carries on again next time.

## The record in each game
Once a run ends, its record goes into the game file itself, so a game passed around (or put on ai-hub) says what made it, what it took and what the agent said about it, including what's only known at the end: time, tokens, cost. It's enough to rebuild the run's place in the dashboard from the game alone (see Reading them back). It's an inert `<script type="application/json" id="cc-matrix-run">` block just before `</body>`: read it in a page with `JSON.parse(document.getElementById('cc-matrix-run').textContent)`, or anywhere with `run-record.mjs` (no dependencies: `readRecord()`, or the commands below). Schema 2; `run-record.schema.json` has every field.

| Section | What it holds |
|---|---|
| `schema`, `tool`, `stampedAt`, `id`, `lab`, `cli` | `2`, `cc-matrix`, when it was written, the run's id (its folder in `runs/`), the model's lab and the CLI |
| `aiHub` | **AI Hub catalogue fields**, named and written the way ai-hub's catalogue has them (its `data/overrides.json`), so an import can take them as they are: `name`, `tagline`, `description`, `type` (Game, Tech demo, Tool), `genre` (from the catalogue's list), `source`, `series`, `players` (`1`, `1–2`, `1–4`), `controls`, `tags` (lowercase), `model` (`Claude Opus 5.5`), `effort`, `harness` (`Claude Code`), `sourceDate` (when the run started, UTC), any `hub:*` field in the game's `<head>` (its session fields), and `provenance` the way ai-hub's import registry keeps it (`sourceKind: cc-matrix-run`, `artifactId`: the run's id) |
| `stages` | only on a run in stages: each step's model, effort, harness, status, time, tokens and cost (`steps`, first to last, this run last) and them added up (`total`). A plan makes no game, so its figures are only in the records of the games built from it. Stamped again after an earlier run was deleted, a record keeps that step's figures from the record already there; `complete` is false when a step was never found |
| `result` | the run's `result.json` as written, everything the dashboard shows of a run (see Notes), minus `sessionId` and `plan` (the account's, not the game's) |
| `prompt` | the prompt as filled for this run (`text`; a stage run's own text is `stageText`), its `template`, its version (`version`, `number`, `savedAt`, `firstRanAt`), the `/goal` message sent (`goal`), and each section's variant (`sections`: `id`, `text` as sent, `hash`) |
| `interview` | the agent's exit interview: `exit-interview.json` parsed (`answers`, each feedback answer with the question it answers), or `error` and the file's `text` when it isn't one JSON object; and its final `reply` |

- **The AI Hub fields** come, lowest first, from what ai-hub reads in the game's `<head>` itself (the title as "Name — Tagline", description, theme colour, `hub:*` tags), the agent's answers under `aiHub`, then what the runner knows for sure (model, effort, harness, sourceDate). Values are put the catalogue's way whatever case or dash the agent used ("shooter" → Shooter, "1-2" → 1–2, "Arcade, 2D" → `["arcade", "2d"]`); "unknown" or an empty value is left out.
- **The exit interview.** The prompt's Source Information section (variant `info-exit`) asks the agent to save its Source Information, its answers to the three feedback lists and the AI Hub fields as `exit-interview.json` beside the game, in a shape it gives, and the 1-shot goal (`on-exit-v2`) checks the file is there and parses (a build stage's goal asks for everything TASK.md says to hand in). A file can be checked; a final reply sometimes comes out empty. Each run records whether it left one (`exitInterview`), and Insights lists the ones that didn't under Needs a look. The reply and an in-game About screen still carry it for people.
- `kb`, `loc`, `todos` and `gameSha256` (a hash of the game as the agent left it) are measured without the record. Paths in it are written from `~` (a reply or an error that names a file).
- `node run-matrix.mjs --stamp` writes the record into every finished run's game, replacing any already there; `--reparse` refreshes the ones that have it. A game whose record would only get a new `stampedAt` is left as it is, so stamping again rewrites only the games whose records changed. Written again, it keeps what only the run knew (the template, each variant's text as sent) from the record already there. Stamping changes the file's bytes, so a game that's already on ai-hub would look new to an import that compares hashes: compare `gameSha256` (or `aiHub.provenance.artifactId`) instead.
- **Reading them back:** `node run-record.mjs export <games or folders…>` prints each record found as a JSON line (`{ file, record }`). `node run-record.mjs rebuild <games or folders…> --out <dir>` makes a runs folder from games alone, the dashboard's run history: each run's `result.json`, prompt, goal, reply, exit interview and game, and the prompt history with its numbers; `node dashboard.mjs --out <dir>` shows it. A folder already there is left as it is. Not in a game, so not rebuilt: the CLI's raw output (`agent.out`), dev files, scores and the session (a rebuilt run can't be resumed). Games stamped with schema 1 (Nov 1–2, 2026) are read in schema 2's shape.

## Resuming failed runs
**Resume failed** (Run → Options, or `--resume-failed`) carries on with a failed run's session where it stopped, instead of starting the run over. It's meant for runs a usage limit cut off partway, so the work they did isn't thrown away.
- **Which runs:** Claude Code only (`claude -p --resume`). A run qualifies if it failed after doing some work (output tokens above 0), its session is still on disk (`~/.claude/projects`), it's in the folder it ran in, with the same model, and, with a time limit, has time left. One that failed on its first request (a limit hit at the start) has nothing to resume. With Retry failed also on, the failed runs that don't qualify start over; without it they're left as they are. Results tags each one that qualifies as "resumable".
- **What's sent:** the run's `/goal` again (from its `goal.md`), so the goal loop carries on, or, without a goal, a short "continue where you left off". The prompt isn't sent again: the session already has it, and `TASK.md` and the work folder stay as they were.
- **What's recorded:** the run keeps its folder, its first start time and what it was made with (prompt version, variant hashes, CLI version). Its time, tokens, cost, turns and tool calls are all its sessions added up, so it compares with runs made in one go, though it also paid to rebuild the context cache when it resumed. `resumes` counts the resumes; `parts` lists each session's start, finish, minutes, exit code and CLI version. ⟳ marks it in Results, and its details list the sessions.
- **How the totals add up:** a resumed Claude Code session reports the whole session's cost, API time and tokens so far, not just its own, because it restores the `cost-state` its transcript saved when the last session ended. The runner reads that saved state before resuming (kept as `since` in `parts`) and subtracts it, so each session counts once. Checked with Claude Code 2.1.312. `--reparse` works the same way, reading each session's output file.
- **The time limit** counts all the sessions: a resumed run gets what's left of it.
- **Ending one** (Stop, ↻, ✕) throws away only the new session's part: the run stays failed and can be resumed again. What it changed in the work folder stays.

## Files
- `matrix.config.json` — everything the CLIs and Setup tabs edit (hand-editable too)
- `run-record.mjs` — the record in each game: writes it (for `run-matrix.mjs`), reads it, `export` and `rebuild` (see The record in each game); `run-record.schema.json` describes it
- `prompt-template.md` — the prompt's headings, with each section's `{{name}}` (see The prompt is its sections); every run also fills `{{model}}`, `{{effort}}` (with `-ultracode` when on), `{{lab}}`, `{{environment}}` (CLI and OS), `{{machine}}` (what this computer has, from `environments/`; below), `{{stamp}}` (when the run started, to the second: `YYYYMMDD-HHMMSS` in the computer's time zone, e.g. `20261029-075312`; the same everywhere in one run, so it ties the game's file name to its run) and `{{date}}` (that moment as `YYYY-MM-DD HH:MM:SS`)
- `environments/<computer>.md` — what each computer has, for the agents that run on it: its processor, memory, space and display, the browsers (with WebGL and WebGPU, and the Chromium flags WebGPU needs where it runs in software), the tools with their versions, Rust's toolchains and which have the wasm32 target, the network, and the date and time all that was checked; then, by hand, what no script can check (no controller to hold, nobody to listen, no second player, no real iPhone) with the stand-ins to use, and how to share the computer with other agents. One file per computer, named after it (`os.hostname()`), so the computers sharing this repo keep their own. `node check-environment.mjs` writes the checked part between its markers and keeps the rest (`--quick` skips starting the browsers); run it after installing or updating anything an agent might use. A prompt or stage text includes the file with `{{machine}}`; a run on a computer without one fails at the start and says to run the script.
- `runs/<run-id>/` — `work/` (the game; the bundled .html in its root, with the agent's `exit-interview.json` beside it), `tmp/` (the run's temp folder; see Runs are isolated), `game-check.png` (the game check's screenshot), `prompt.md`, `reply.md`, `result.json`, `agent.out` (everything the CLI printed: for Claude Code, Grok and agy the whole event stream, a few MB for a long run), `agent.err`; a resumed run has each later session's as `agent.2.out`, `agent.2.err` and so on. `unfinished.json` while the run's agent works, and after, in a run that was cut off (see Restarting the dashboard)
- `runs/.session.json`, `runs/.batches/` — the batch going (or cut off) and each batch's copy of the config and prompt, kept until it ends, so it can be picked up after a restart or quit (not committed)
- `runs/prompt-history.json` — every version of the prompt a batch has run: its number, hash, when it was last edited (`at`) and first ran (`ranAt`), and its text (Setup → Prompt history)
- `runs/scores.json` — your scores, notes and "looked at" marks, each saved with the run's `startedAt`: a re-run starts unreviewed, and deleting a run deletes its review. `runs/.smoke.json` — the latest Test result per model
- `runs/results.csv` — everything in one spreadsheet; `runs/index.html` is a static gallery
- `audit.json` — what the Audit tab shows
- `test/` — tests (below) and `test/fake-cli/`, stand-ins for the five CLIs that print each one's real output format

## Notes
- Finished runs are never redone unless you tick Retry failed or Resume failed, or delete the run (✕ in Results). A run is known by its variants' short names, so a short name stands for one text. Editing the text of a variant that has finished runs gives it a new short name as you type: made from the new text when the old name was made from the old one (`alien-soldier` → `golden-axe`), else `-v2`, `-v3` …; a text that ran before gets that variant's name, so its runs count, and putting the old text back puts the old name back. A name finished runs used for other text is taken (Setup won't save it). Text read back from the runs' prompts (`/api/variants`, checked against each run's `variantHashes`) is what + Add… offers under Ran before. A variant whose text was edited before this (or by hand in the config) has finished runs that used its earlier text: Setup and Insights warn about it, and `node run-matrix.mjs --rename-variant perspective:pov-engine=pov-native` gives those runs a name of their own, in `result.json` and the game's record (`--dry-run` lists them first; `@hash` before the `=` picks one text when there were several). Stopping a batch discards only the runs still in progress (so does ending one with ↻ or ✕).
- Editing the prompt doesn't redo anything either: each run keeps the prompt version it was made with, so compare versions by prompt in Results → Compare. Nor does adding a dimension (a new field in the prompt): runs made before it count as one of its variants, set in that dimension's card in Setup ("They count as …"; `"olderRuns": true` on the variant in the config, else the first variant). They show, filter and compare as that variant (in `results.csv` and the gallery too), and their details say "before this field". Removing a dimension leaves its runs counting for the variants that are left.
- Agents run with permission prompts off. Use a dedicated machine, VM or container. The dashboard only listens on this computer (127.0.0.1), and only answers its own page: a request with another `Host` (DNS rebinding) is refused, and so is a write from another website (it needs JSON from the dashboard's own origin). To reach it through a tunnel (e.g. `phone-preview`), start it with `--allow-host <tunnel host>`: anyone with that URL can then start agents.
- **Runs are isolated** (`"isolate": false` in the config turns it off): nothing of this computer's own setup, or of another run, gets into a run, so runs compare. No run can open a window: `DISPLAY` and `WAYLAND_DISPLAY` are unset for agents, so a headed browser fails instead (`xvfb-run` still works). Claude Code loads no `CLAUDE.md`, no MCP servers (`--strict-mcp-config`) and no auto memory: the run folders are inside this repo, so runs would otherwise read and write the memory Claude Code keeps for it (one did, on 2026-11-03). Grok loads no memory and nothing of Claude Code's (its `CLAUDE.md`, skills, rules, MCP servers, hooks), Muse no other CLI's rules or skills (`--no-foreign-personal-context`). No switch was found for `~/.codex/AGENTS.md` (Codex), `~/.grok/AGENTS.md` (Grok) or `~/.gemini/GEMINI.md` (agy), nor for Codex's and Grok's own plugins: those still load, so keep them neutral or the comparison is skewed. The CLIs card lists each CLI's global instruction files, the skipped ones marked so. Run → Preview shows each run's environment as an `env …` prefix, and `isolated` in `result.json` says which runs had it.
- **Each run has a temp folder of its own**, `tmp/` beside `work/`: `TMPDIR`, `TMP`, `TEMP` and `CLAUDE_CODE_TMPDIR` point there, so tools that make temp files don't fill the shared /tmp (in memory on some computers; all 24 planners of Nov 3 filled it). It isn't copied to a later stage, and it's deleted once the run has finished, OK or not (a cut-off run keeps it to carry on with); `runs/*/tmp/` is in `.gitignore` for the ones still going. **What an agent leaves running is stopped** once it exits: a process started since the run did, with no terminal (never someone's shell), whose working folder or command line is in the run's folder, like a test server it never stopped (Claude Code runs background commands in a session of their own, so ending the agent missed them). Their command lines go in `leftovers`. Linux only.
- **The game check** (`"gameCheck": { "seconds": 60 }` in the config, or `true` for 60): once a run has left a game, the runner loads it in headless Chromium (software WebGL, and WebGPU on SwiftShader with `--enable-unsafe-webgpu --enable-features=Vulkan --use-webgpu-adapter=swiftshader`, which WebGPU engines need there) with `check-game.py`, leaves it alone for that long (long enough for most attract modes to start: they wait 10 s of the game's own time, which a slow software renderer stretches), and records what it threw, logged as an error or failed to load, with a screenshot (`gameCheck` in `result.json`, `game-check.png`). It's in the run's details, Needs a look flags a game with errors, and Expectations counts them. It needs Playwright for Python and its Chromium; without them it says skipped and runs go on as before. It adds about a minute to a run. `node run-matrix.mjs --check-games` checks the finished runs that haven't been. It's kept out of the game's record, so checking later never changes a game file. A WebGPU canvas drawing about a frame a second in software can come out blank in the screenshot; its errors are what count.
- Cost (`costUsd`) is only what the CLI reports: Claude Code (the API-equivalent price, also on a subscription) and Grok (at its own rate, about a third of grok-4.7's list price). Codex, agy and Muse don't report cost, so they show n/a. To compare all of them, use the list price (`apiCostUsd`, "list $" in Results; see What each CLI reports).
- Tokens: input counts everything sent, cached included (agy's own `input_tokens` leaves cache reads out, so they're added). Output includes reasoning.
- Token breakdown: `uncachedInputTokens` + `cachedTokens` (cache reads) + `cacheWriteTokens` = `inputTokens`; `totalTokens` = input + output. Cache writes are only reported by Claude Code, Grok and Codex (blank otherwise). `reasoningTokens` is the thinking count (part of output). `result.json` also has a per-model split (`models`), which the list price is worked out from; for Claude Code it has the cost per model, matching `/usage`. After changing a parser or a price, `node run-matrix.mjs --reparse` refreshes these fields from each run's saved `agent.out` and the CLIs' session logs.
- Also recorded per run:
  - `cliVersion`: the CLI's version when the batch started (a filter and Compare field as "CLI version"). CLIs are never updated automatically, so an update only happens when you choose it.
  - `promptVersion`: a hash of the prompt template. The runner numbers it v1, v2 … in `runs/prompt-history.json` when a batch first runs it (from the dashboard or a terminal), so however many times the prompt is edited between batches, that's one new version; going back to an earlier text runs as that earlier version. A version only found in runs (from before the history, or if the file is lost) gets a number at the next batch, dated by its first run, without its text.
  - `rounds`: Claude Code's result rounds (one per /goal round). `turns` counts all of them (for runs before stream-json, only the last).
  - `apiCalls` (model requests), `toolCalls` with `tools` (calls per tool name) and `toolErrors` (calls that failed, including commands that exited non-zero), `compactions` (context summarized to make room), `firstTokenMs`, `plan`, `helpers`, `sessionLog`: see What each CLI reports. Each is blank where the CLI doesn't give it.
  - `subagents`, `replyChars` (length of the final reply: the CLI's result, or, when Claude Code ends a /goal turn itself and its result is empty, the agent's last response, which is also what `reply.md` holds) and `todos` (TODO/FIXME left in the game file).
  - `variantHashes`: a short hash of each variant's text, so the dashboard knows exactly which runs used text that has been edited since (older runs are checked against their saved prompt instead).
  - `stageHashes`: on a run in stages, the same for its stage's `text` and `goal` as set (not filled in); older runs are checked against their `prompt.md` and `goal.md`.
  - `resumes` and `parts`, on a resumed run: see Resuming failed runs.
  - `exitInterview`: whether the run left the exit interview its prompt asks for, `ok`, `invalid` (not one JSON object) or `missing`; blank when its prompt doesn't ask for one, and for a plan.
  - `plannerInterview` and `plannerAnswers`, on a stage run whose Instructions ask for `planner-exit-interview.json` (the plan stage's do): the agent's review of the prompt it was given, saved in its folder as a JSON list of `{ "question", "answer" }`. `plannerInterview` is `ok`, `invalid` or `missing`; `plannerAnswers` holds each question with its answer, so answers still read right after the questions change (a plan makes no game, so they're kept here rather than in a game's record). The next stage isn't given the file. In Results: the run's details list them, **review** opens the file, and Needs a look flags a missing one.
  - `goalMet`, `goalChecks`, `goalForced`, `goalReason`: how a Claude Code run's /goal went, read from its transcript (`~/.claude/projects`; the CLI's own output doesn't say). `goalMet` is whether its last goal check passed (false when it never got one, like a session that failed first; a run that finished without any check giving a verdict shows as unknown), `goalChecks` how many checks it got, `goalForced` that Claude Code ended the turn itself after the check had blocked it 9 times in a row (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`, 8 by default), so the run finished without its goal, and `goalReason` what the last check said was missing. A run's `status` stays as it was: `ok` means the CLI finished, `goalMet` whether the goal check agreed. Blank for runs sent no /goal, for other CLIs (which don't save their checks where they can be read) and for runs whose transcript isn't on this computer. In Results they're the **goal met** column and filter (yes, no, unknown, or skipped for a CLI that got the plain prompt), a column in Averages by group, a line in a run's details, a check in Insights and a flag under Needs a look.
  - `contextWindow`: on a Codex run, the context the model could use, in tokens, as Codex reported it in its session log (95% of the model's window: 997,500 for a 1.05M window). It comes from `~/.codex/config.toml` (`model_context_window`) capped by the model catalog Codex reads, so a model missing from a catalog of your own (`model_catalog_json`) gets Codex's default, 272K (258,400 usable): GPT-6.1 Terra did until Nov 5, 2026, and compacted its context about 60 times a build. Shown in a run's details; `--reparse` fills it in where the session logs are on this computer.
  - `timeZone`: this computer's time zone, as the run started: its folder name and `{{stamp}}` are local time.
  - `isolated`: whether the run was isolated (see Runs are isolated, below); blank for runs before 2026-11-03.
  - `gameCheck`: what the runner saw when it loaded the run's game once, headless, with `gameCheck` on in the config (see The game check): `pageErrors`, `consoleErrors` and `failedRequests` (counts, and the first few as `pageErrorsFirst` and so on), `loadMs`, `seconds` and `shot` (its screenshot), or `skipped` (why) or `error`. Not in the game's record.
  - `leftovers`: what the run's agent left running once it exited (a test server it never stopped, say), stopped by the runner: their command lines.

  `--reparse` fills in all of these except `cliVersion`, `promptVersion` and `timeZone` for older runs (the goal fields where their transcripts are on this computer), and writes `reply.md` for a run that has none when its output has a reply (a /goal run Claude Code ended itself, parsed before the reply was read from its last response).
- The budget only counts reported cost. Once it's reached no new run starts; runs already going finish and are kept.
- `result.json` (and so `runs/` if you commit it) holds each run's plan usage and tier, and its session ID. Account balances and credits aren't recorded.
- A run that can't start (a `{{placeholder}}` its variant leaves unfilled, a /goal over 4,000 characters) is recorded as failed with the reason, and the batch carries on.
- agy gets the prompt as an argument (its `-p` reads neither stdin nor a file). On Windows, very long multi-line prompts can break through the shell; WSL avoids that.
